# ADR-001: Use calendar-based recurring task instances

## Status

Accepted

## Context

小序需要支持每天、工作日、每周、每月、每年和自定义间隔的重复任务。重复计划必须保持用户原先选择的日历节奏，即使某次任务逾期完成，也不能把整个计划移动到完成日。应用还需要保留已完成记录，并能在未来的 Tauri 客户端中将每次提醒注册给操作系统。

## Decision

在 `Task` 上保存结构化 `RecurrenceRule`，由 `unit`、`interval` 和月/年规则所需的锚定日期组成。完成重复任务时保留当前实例，并生成一个新的任务实例；新实例沿用项目、标签、优先级、描述和重复规则。下一截止时间从原截止时间向前推进，直到得到严格晚于当前时间的最近一次，从而跳过已经错过的周期。

提醒相对于截止时间的偏移量会被保留。新任务设置截止时间时，提醒默认与截止时间相同；用户手动调整提醒后，后续实例延续这段偏移。每月 29、30、31 日遇到较短月份时取该月最后一天，但规则仍保留原锚定日，因此后续较长月份会恢复到原日期。

## Consequences

### Positive

- 固定日历节奏符合用户预期，逾期完成不会造成计划漂移。
- 已完成实例保留，历史记录清晰。
- 结构化规则便于测试，并可映射到各平台的本地通知 API。
- 旧数据没有重复规则时仍然有效，不需要破坏性迁移。
- 已存在后继实例时不会重复创建，恢复并再次完成旧实例仍保持幂等。

### Negative

- 一个重复系列会逐渐产生多个任务实例。
- 修改当前实例不会自动修改整个系列；系列级编辑需要后续单独设计。
- 浏览器关闭后仍然无法可靠触发提醒，需等待 Tauri 阶段。

### Neutral

- 恢复一个已完成实例不会自动删除已生成且后来被编辑的下一实例。

## Alternatives Considered

按完成时间顺延会让“每周一”逐渐漂移到其他星期，因此未采用。反复改写同一个任务对象虽然更简单，但无法保留已完成历史，也不利于未来的系列管理。一次性生成所有未来实例会制造大量数据，并使修改规则变得复杂，因此未采用。
